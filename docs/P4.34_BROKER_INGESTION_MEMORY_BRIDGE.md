# P4.34 — Broker ingestion to persistent memory bridge

## Pipeline

`ingest_and_persist_broker_batch` connects the P4.33 reconciliation gate, P4.31
point-in-time broker descriptors, and P4.32 DuckDB memory storage:

1. Reconcile the complete caller-supplied batch against verified broker IDs,
   verified sessions, timezone-aware session-finality timestamps, source inventory,
   payload hashes and optional contract totals.
2. Stop without writing if the ingestion report is not memory-eligible.
3. Convert accepted observations to the strict descriptive-only memory input.
4. Apply both the event-date cutoff and an exact timezone-aware availability
   timestamp cutoff. Same-day observations arriving after the requested cutoff
   are excluded.
5. Stop without writing if any accepted row is excluded by memory admission.
6. Derive daily/weekly/monthly/yearly descriptors and persist them as one
   DuckDB transaction. A changed payload under an existing idempotency key
   aborts and rolls back the entire append batch.

## Atomic persistence

`BrokerMemoryStore.append_many` now validates all snapshots before opening a
transaction, checks all idempotency keys, inserts new rows and commits once.
Exact retries are reported as replays. A conflicting key or any insert failure
rolls back every write in that batch. Existing single-snapshot `append` remains
available.

## Point-in-time behaviour

The descriptor builder now requires every observation's `available_at` to be a
timezone-aware ISO timestamp. Callers may supply `available_by` as a timezone-
aware timestamp (datetime or ISO string); observations later than that exact
cutoff are excluded, even when they arrived on the same calendar date.

## Safety and limitations

- Only reconciled, complete batches can reach the memory stage.
- Any row excluded by memory admission blocks the entire batch; no partial
  memory persistence occurs.
- Stored records remain `descriptive_only`. No beneficial ownership, operator
  intent, accumulation/distribution, manipulation or BUY/SELL signal is inferred.
- The bridge accepts supplied extracts; it does not fetch broker data from
  NEPSE, ShareSansar, Chukul, NepseAlpha or other providers.
- Broker/session/finality/source registries must be independently verified.
- DuckDB atomicity applies to one local database transaction. This does not
  establish multi-host concurrency, cloud durability, backup or restore.
- Production eligibility remains false.

## Tests

Covers eligible persistence, daily/weekly/monthly/yearly output, exact replay,
source-coverage rejection, intraday late-arrival rejection, contract mismatch,
and all-or-nothing rollback when a later idempotency conflict occurs.
