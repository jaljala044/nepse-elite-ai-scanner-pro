# P4.6 — immutable signal and outcome store

## Purpose
`backend/app/signal_store.py` persists frozen research-only signal envelopes and subsequent horizon outcome observations in the existing DuckDB API research store. It is a separate research ledger, not the canonical OHLCV warehouse.

## Invariants
- A signal must pass `verify_signal` hash validation before storage.
- Only `NO TRADE` research records are accepted; production BUY/SELL/HOLD authorization remains disabled.
- Signal identity is the SHA-256 content hash generated by the frozen signal contract.
- Identical retries are idempotent. A conflicting payload for an existing ID is rejected.
- Outcomes require an existing signal and the same horizon as the frozen signal.
- Outcome observation time must be timezone-aware and cannot precede the signal decision time.
- Outcome records are content-addressed and append-only. Repeated identical observations are idempotent; no update/delete API is exposed.
- JSON NaN/Infinity values are rejected.

## Scope and limitations
Stored outcomes are descriptive research references. They do not prove exchange fills, settlement eligibility, price-limit execution, fees, or strategy profitability. `horizon_outcomes.py` forward close references remain distinct from execution simulation. Walk-forward validation and signal accuracy remain blocked until verified historical outcome inputs and execution assumptions are independently reviewed.

## Verification
Synthetic unit tests cover hash verification, idempotent persistence, immutable tamper rejection, signal/horizon linkage, time ordering and non-finite JSON rejection. These tests validate storage mechanics only; they do not establish live performance.
