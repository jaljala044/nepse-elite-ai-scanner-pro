# P4.34 — Broker memory promotion boundary

## Purpose

P4.34 adds the explicit boundary between P4.33's reconciled broker-ingestion output and persistent broker memory. It is a fail-closed coordinator, not a source connector, scheduler, analytics engine, or trading signal.

## Admission rules

A batch is blocked unless all of the following are true:

- P4.33 reports `coverage_status=COMPLETE`.
- Accepted-row count equals the supplied record count and is non-zero.
- Quarantine count is exactly zero.
- Reconciliation and validation passed.
- Source rights, exchange session and point-in-time checks are explicitly cleared.
- Source payload and source-manifest SHA-256 digests are present in the expected format.
- Session date and availability timestamp are present.

Missing evidence is a block, never a neutral value. Partial coverage is not converted into zero broker flow.

## Atomic persistence contract

The store adapter must implement `append_batch` transactionally:

- Same batch idempotency key + same canonical record digest => `REPLAYED`, no new rows.
- Same idempotency key + different digest => `CONFLICT`, no mutation.
- New valid key => append all records and commit atomically.
- Any exception or interrupted transaction must leave no partial batch.

The coordinator does not claim that a particular database adapter satisfies these properties until an integration test proves it. It also does not silently retry a conflict.

## Point-in-time and evidence lineage

The promotion call carries the source session date and availability timestamp unchanged. The adapter must persist those values alongside source lineage and methodology version. Downstream reads must apply both event-time and availability-time cutoffs to prevent look-ahead.

## Scope limits

- No live NEPSE or third-party source acquisition is implemented.
- No scheduler, backfill or production deployment is enabled.
- Broker codes remain execution-channel identifiers, not beneficial-owner identities.
- Promotion records are descriptive observations only; they do not establish accumulation, distribution, ownership, manipulation or intent.
- No BUY/SELL/HOLD action, probability, or production eligibility is emitted.
- The supplied digest format check is not cryptographic authentication of a publisher; upstream verification remains mandatory.

## Integration sequence

1. Adapt the exact P4.33 reconciliation result into `ReconciliationEvidence`.
2. Pass only the rows accepted by P4.33; do not reconstruct or repair quarantined rows here.
3. Implement the transactional store adapter against the P4.32 append-only store.
4. Add integration tests for atomic rollback, exact replay, changed-payload conflict, restart recovery and as-of retrieval.
5. Keep promotion disabled until the dependency PRs are merged in order and CI passes on the exact head.
