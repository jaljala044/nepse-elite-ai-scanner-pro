# P4.36 — Daily Broker History Ledger

## Step 1 of the P4.36/P4.37 sequence
Introduces an append-only DuckDB ledger for validated broker/security/session observations and a separate daily completeness manifest.

## Admission contract
A row is accepted only from a P4.33 \`IngestionReport\` with \`memory_eligible=True\`, one session date per batch, descriptive-only status, verified broker/security identity, source/evidence lineage, valid payload hash, non-negative exact decimals, and coverage >=95%.

A session manifest is also mandatory and must attest:
- complete source inventory and source coverage >=95%;
- reconciled source control totals;
- complete P4.35 identity coverage, with minimum coverage >=95%;
- verified exchange session;
- timezone-aware availability timestamp.

The manifest and all daily rows are written in one DuckDB transaction. Exact replay is a no-op; changed content under the same natural key or a changed session manifest is rejected and rolled back.

## Point-in-time access
Reads require both an event-date cutoff and timezone-aware availability timestamp. Late-arriving data remains hidden from historical as-of queries.

## Critical missing-data rule
The ledger does not manufacture zero rows. P4.37 may interpret an absent broker/security observation as zero activity only for a session with a stored complete-source, reconciled, identity-complete manifest. Otherwise that pair/session is unknown and must reduce coverage.

## Scope
This is a storage and validation layer for caller-supplied normalized extracts. It does not fetch provider feeds, authenticate publishers, or assert beneficial ownership/intent. All stored activity remains descriptive-only.
