# P4.32 — Persistent Broker Behaviour Memory

Status: implementation foundation submitted for review; not yet production-enabled.

## Storage design
- DuckDB append-only snapshot table with primary key snapshot ID and unique idempotency key.
- Canonical JSON payload plus SHA-256 content hash.
- Immutable methodology version, event as-of date, availability timestamp and creation timestamp.
- Exact replay returns the original snapshot; reuse of the same idempotency key with changed content raises a conflict.
- New run keys create new immutable versions; previous snapshots remain queryable.
- Point-in-time retrieval applies both event-date and availability-time cutoffs.
- Only `descriptive_only` broker memory snapshots can be stored.

## Guarantees and limits
- The API exposes append and read operations only; no update/delete operation is provided.
- Database constraints enforce unique snapshot IDs and idempotency keys. DuckDB does not provide the same row-level immutability trigger semantics as a dedicated append-only event store; direct database-file access remains privileged and must be controlled operationally.
- This is a persistence primitive, not a production deployment, scheduler, API endpoint, broker ingestion pipeline or signal generator.
- No canonical market data admission or trading-readiness gate is changed.

## Tests
Covers restart persistence, exact replay, idempotency conflict, version retention, point-in-time visibility, descriptive-only admission, timezone-aware availability and batch replay.
